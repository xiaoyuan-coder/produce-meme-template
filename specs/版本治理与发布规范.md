# 版本治理与发布规范

## 1. 当前问题证据

现有 Unified 已经出现清晰的版本漂移：

- Git 工作区中的主 Skill 标注为 `1.7.0`。
- Git 提交基线仍是 `1.6.0`。
- README 仍写 `1.5.5`。
- 本机安装副本标注为 `1.7.1`，并含有源码仓库没有的文件。
- Unified 和拆分仓库都存在大量未提交修改，难以确认某次生产实际用了哪一组规则。

因此，新 Skill 需要从第一天建立“源码、发布包、安装副本、生产批次”四层隔离。

## 2. 三类版本分别管理

| 版本 | 含义 | 例子 |
| --- | --- | --- |
| `skillVersion` | Skill 行为与知识版本 | `1.2.0` |
| `artifactSchemaVersion` | 内部阶段产物 Schema 版本 | `1.0.0` |
| `galleryContractVersion` | 正式模板业务合同版本 | 由上游正式规范决定 |

三者禁止共用一个版本号。Skill 升级不会自动宣称正式模板 JSON 合同升级。

## 3. 单一版本事实源

源码仓库中只有 `release.json` 可以人工修改 Skill 版本：

```json
{
  "skillName": "produce-meme-template",
  "skillVersion": "1.0.0",
  "artifactSchemaVersion": "1.0.0",
  "supportedContracts": {
    "galleryTemplate": "current-cover-contract"
  }
}
```

`package.json`、`agents/openai.yaml` 或其他需要版本的文件由脚本生成或校验。SKILL.md 标题、README、参考文档文件名不写会频繁变化的版本号。

## 4. 外部契约快照

每份外部正式合同以只读快照放入：

```text
contracts/upstream/<contract-name>/<contract-version>/
```

同时记录来源、获取日期、内容摘要和兼容范围。当前版本冻结用户确认的正式数据口径、现有 Schema，以及《最新正式数据样例合同审计》中两份样例的路径与 SHA。研发侧 `gallery-template-authoring-spec`、import README、Worker 编译和提示词拼接实现不属于本 Skill 合同；数据侧不据此承诺后端行为。

外部合同升级流程：

1. 新增快照，不覆盖旧快照。
2. 运行合同差异检查。
3. 明确兼容、需迁移或阻断。
4. 更新适配器和 fixtures。
5. 升级相应合同版本范围；只有 Skill 行为变化时才升级 `skillVersion`。

## 5. 机器规则单一来源

下列内容只能在机器可读文件中定义一次：

- 目标类别、槽位类别和图片操作类别。
- 阶段状态和允许的状态迁移。
- Schema、必填字段和条件规则。
- instruction 段落、长度和编译结构。
- 媒介、形态、接触和替换依赖枚举。

Python、JavaScript、文档示例和测试都消费同一份定义。文档只解释含义，验证器不能各自复制一份枚举。

## 6. 不可变发布包

发布前必须满足：

- Git 工作区干净。
- 单元、fixture、Schema、引用完整性和端到端 smoke test 全部通过。
- `release.json` 的 SemVer 变化符合兼容性。
- 所有 reference 链接和脚本入口存在。
- 外部合同快照内容摘要可验证。

发布脚本生成 `release-lock.json`，至少包含：

- Skill 版本。
- Git commit。
- 构建时间。
- 全部发布文件的相对路径与 SHA-256。
- 内部 Schema 和外部合同版本。
- 编译器、验证器与 fixture 集摘要。

发布产物写入不可变目录：

```text
dist/produce-meme-template/1.0.0/
```

已经发布的目录不能原地修改。任何行为修改都创建新版本。

## 7. 安装副本治理

安装目录不允许手工编辑。安装只接受经过验证的发布包：

1. 校验 `release-lock.json`。
2. 安装到版本目录。
3. 运行 smoke test。
4. 原子切换 `current` 指针。
5. 保留上一版本用于回滚。

启动生产前执行 `doctor`：

- 当前安装版本是否等于请求版本。
- 安装文件摘要是否和 release lock 一致。
- 是否存在安装目录额外文件。
- 外部合同是否在支持范围。

任一检查失败时停止生产，并输出可操作的修复建议。禁止临时改安装副本后继续跑批。

## 8. 生产项运行 pin

每个生产项在 P0 创建不可变 `production-pin.json`：

```json
{
  "skillVersion": "1.0.0",
  "releaseDigest": "sha256:...",
  "gitCommit": "...",
  "artifactSchemaVersion": "1.0.0",
  "galleryContractVersion": "...",
  "replacementSpecVersion": "1.0.0",
  "validatorDigest": "sha256:..."
}
```

该生产项的阶段产物引用同一 pin。批量提交默认不共享 pin；多个生产项恰好使用同一 release 时仍分别记录。一个运行中的生产项不会因本机安装了新版本而静默切换规则。

需要中途升级时：

1. 暂停受影响生产项。
2. 生成旧 pin 与新 pin 的差异报告。
3. 标明受影响生产项和需要失效的阶段。
4. 创建显式迁移记录。
5. 从最早受影响阶段重新执行。

## 9. 模板 revision 与 Skill version 分离

- `skillVersion` 表示生产工具行为。
- `templateRevision` 表示某个模板数据的业务修订。
- `sharedPolicyRevision` 只在用户显式启用共享批次策略时，表示该共享策略的修订。

同一 Skill 版本可以产出多个模板 revision；升级 Skill 也不会自动改写已有模板。T1 测试报告必须绑定被测 `gallery-template.json` 的 SHA、`templateRevision`、模板图 URL 和测试器版本。真实生图测试产生的问题通过新模板 revision 修复，原测试记录保持不可变。

## 10. SemVer 规则

- **MAJOR**：阶段合同、正式输出语义或调用方式不兼容。
- **MINOR**：兼容地增加规则、能力、字段适配或检查项。
- **PATCH**：修正文案、脚本缺陷、fixture 和不改变合同的判断错误。

只修改内部参考文档但导致判断行为变化时，仍需要升级 Skill 版本。版本判断依据是行为影响，不依据文件类型。

## 11. CI 与发布门槛

最低发布检查：

1. `validate_skill`：Skill 结构和引用完整。
2. `validate_contracts`：Schema 和外部快照完整。
3. `test_rules`：受控枚举、决策树和状态机。
4. `test_fixtures`：历史 GoodCase/BadCase。
5. `test_compilers`：ReplacementPlan、GenerationPackage、正式 JSON 编译。
6. `test_version_drift`：所有声明版本一致，安装包无额外文件。
7. `smoke_e2e`：最小样例从网图走到本地待上传数据；真实 API 可用性由单独集成测试覆盖。

生产切换前还需要在真实批次影子运行，对比旧入口和新入口的语义、视觉、字段与失败率。
