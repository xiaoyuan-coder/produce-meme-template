# 可见文字区域与文字槽合同

## 1. 先建立完整文字清单

P3 只读取 Approved Template Image。每一组具有独立空间、语义或视觉职责的可见文字都形成一个 `Text Region`，并先标注机器合同中的文字角色：正文、归因、水印、品牌或歧义。区域清单必须完整、ID 唯一，并为声明语种、逐 token 内容、换行、大小写敏感 token、罕见符号和必要符号拓扑提供图像证据。实际语种由独立语义审计逐区域观察并与声明值对账；简体、繁体、日文、韩文、英文和混合语种使用机器合同中的具名值。

每个区域只选择一个处理动作：开放槽位、保留在全文编辑、固定保留、清理或复核。水印只能清理；歧义文字只能复核；归因、品牌和低价值信息不能伪装成高价值文字槽。

## 2. 文字槽准入

只有三类文字可以成为结构化控件：

1. 与主体身份绑定且具有独立编辑价值的短文字；
2. 文字卡、主标题、核心口号或承担笑点的主要视觉文字；
3. 从长文中抽取、能够独立改变含义的高价值词或短语。

文字槽必须通过通用四道价值门禁，并与恰好一个文字区域和该区域的实际选中文字双向绑定。长段落不能整体进入一个槽；精确画内文字可以凭当前 Approved Template Image 证据获得默认值长度例外，仍不能用例外绕过整段文字门禁。文字推荐项继续受短文字排版容量约束。

装饰微字、版权/出处、氛围填充、品牌标记和没有独立编辑价值的海报信息不占槽位预算。需要清理的文字也不进入 Prompt Template。固定或清理区域的完整文字与有意义 token 都要和用户内容对账，并统一执行 NFKC、大小写、空白和标点归一；完整文字使用包含关系，单 token 使用归一化等值，避免共享词误锁无关内容。工作流还从原文独立提取英文、数字和连续中文 span，adapter 不能通过合并 token 隐藏低价值文字来源。

## 3. 自由编辑与精确保真

次要可读文字具有编辑价值时，使用 `free_editable` 动作，同时原样进入 `freeEditableContent` 和 Prompt Template；它不会出现在 `inputSchema`。固定视觉文字只保留版面或语境职责，不自动获得用户控件。

文字默认值必须来自当前文字区域的实际文字。高价值长文槽使用原文中的短 span；主要视觉文字与身份文字按图中真实语言、token、换行、大小写和符号拓扑保存。未经显式转换策略，不把默认值翻译成另一语种。主体开放时，身份相关文字由独立语义审计逐区域判断是否中性；合同不使用封闭词表限制合法的中性标题、称谓或界面文案。

## 4. 双层验收

工作流核心确定性检查区域覆盖、字段形状、可判定的脚本组合、token/换行/大小写/符号保真、角色—动作兼容、槽位双向绑定、段落容量和自由编辑落点。独立语义审计再按相同区域 ID 复核每个角色、价值类别、动作、实际语种、观察 token 和身份中性结论，并为全部槽位与每条自由编辑内容声明 `originTextRegionId` 或无文字区域来源。槽位来源只允许指向双向一致的 `open_slot` 区域，自由编辑来源只允许指向内容一致的 `free_editable` 区域；核心会重算这些明确来源，已知来源不能声明为 `null`。审计还要返回完整 Prompt、自由内容和全部槽值中的 fixed-region leak ID，核心要求严格为空。固定身份路线中已同步到新主体的身份文字沿用身份合同，不作为开放主体文字泄漏。全部审计证据绑定完整内容摘要，任一层失败都在上传前停止。

机器字段、角色、动作、价值类别、语言值和容量只读取 `contracts/machine-rules.json` 的 `visibleTextContract`。
